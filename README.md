# PCARP Abstraction

This project extends the [PCARP pipeline](https://github.com/kieker-monitoring/PCARP) with model abstraction between MOP (model merging) and MVIS (graph generation). The abstraction stage produces a MAB model; MVIS and the grouped graph visualizer turn it into a component graph and an SVG.

Run the commands below from the repository root. The script writes results under `bin/<output-name>/`.

## Requirements

- Java 17 or newer and compiled abstraction classes in `tools/abstraction/out/`.
- Python and the DAR, SAR, MOP and MVIS executables under `tools/oceandsl-tools/bin/`.
- A working Tulip installation: set `TULIP_ROOT` to the directory containing `bin/python3` and `lib/`. The Tulip Python bindings and the packages used by the grouped graph visualizer must be available to that interpreter.
- For a full or MOP-only run: dynamic analysis logs for DAR and static analysis input for SAR. An existing MOP model is sufficient for an abstraction-only run.

Use `bash scripts/pipeline.sh` instead of `./scripts/pipeline.sh` if the script is not executable.

On a fresh checkout, compile the Java stage before running the pipeline (generated `.class` files are not stored in Git):

```bash
mkdir -p tools/abstraction/out
find tools/abstraction -maxdepth 1 -name '*.java' ! -name '*Test.java' ! -name 'AbstractionTestBase.java' -print0 |
  xargs -0 javac -cp 'tools/oceandsl-tools/lib/*' -d tools/abstraction/out
```

The `tools/oceandsl-tools/bin/` executables must also be installed or restored in a fresh checkout; they are not generated by the abstraction compiler.

## Pipeline modes

### Full pipeline

```bash
./scripts/pipeline.sh <dynamic-logs-dir> <static-input-dir> <output-name> <mode> <arg1> <arg2> <arg3> <arg4>
```

Runs DAR, SAR, the SAR model conversion, MOP, MAB, MVIS and Tulip. For example:

```bash
./scripts/pipeline.sh data/uxsim/dynamic-logs apps/UXsim uxsim-pda1 PDA 1 0 0 0
```

Replace the example input paths with the dynamic-log directory and the static-analysis input directory on your machine. Results appear in `bin/uxsim-pda1/`.

### MOP only

```bash
./scripts/pipeline.sh --mop-only <dynamic-logs-dir> <static-input-dir> <output-name>
```

Runs DAR, SAR, the SAR model conversion and MOP, then stops. For example:

```bash
./scripts/pipeline.sh --mop-only data/uxsim/dynamic-logs apps/UXsim uxsim-base
```

The resulting merged model is in `bin/uxsim-base/mop_model/`. This mode does not produce a visualization.

### Abstraction only

```bash
./scripts/pipeline.sh --abstraction-only <mop-model-dir> <output-name> <mode> <arg1> <arg2> <arg3> <arg4>
```

Reads an existing MOP model, then runs MAB, MVIS and Tulip. DAR, SAR and MOP are skipped. For example:

```bash
./scripts/pipeline.sh --abstraction-only bin/uxsim-base/mop_model uxsim-pda1 PDA 1 0 0 0
```

The input MOP directory is left untouched. This mode is useful for comparing abstraction configurations on the same recovered model.

## Abstraction modes

The first argument after `<output-name>` selects the mechanism. **Always pass four additional arguments**; use `0` for unused positions. Threshold parameters use percentages on the 0–100 scale, not fractions.

| Mode | Mechanism | Example arguments after the output name |
| --- | --- | --- |
| `I` | Identity: pass the model through without abstraction | `I 0 0 0 0` |
| `PDA` | Package-depth aggregation; `arg1` sets the package depth | `PDA 1 0 0 0` |
| `PTA` | Percentage-based threshold aggregation; `arg1` is a percentage | `PTA 25 0 0 0` |
| `CTA` | Percentile-based threshold aggregation; `arg1` is a percentile | `CTA 99 0 0 0` |
| `PTF` | Percentage-based threshold filtering; `arg1` is a percentage | `PTF 1 0 0 0` |
| `CTF` | Percentile-based threshold filtering; `arg1` is a percentile | `CTF 99 0 0 0` |
| `C` | Communication-based clustering with automatic parameter selection | `C 0 0 0 0` |
| `CS` | Sequential composition: `arg1`/`arg2` are the first mechanism/value; `arg3`/`arg4` the second | `CS CTA 85 CTF 85` |
| `CF` | Composition with thresholds determined from the original model before either step | `CF CTA 85 CTF 85` |

For composition, select a mechanism and its value for **each** step (for example, `PDA 1`, `PTA 25`, `CTA 85`, `PTF 1`, or `CTF 85`). In `CS`, the second step calculates any threshold using the model produced by the first step. In `CF`, percentage/percentile thresholds for both steps are calculated from the input model before applying the steps. A threshold-based filtering step still selects components from the model it receives.

Example: compare identity with a fixed-threshold composition using the same MOP input:

```bash
./scripts/pipeline.sh --abstraction-only bin/numpy-base/mop_model numpy-identity I 0 0 0 0
./scripts/pipeline.sh --abstraction-only bin/numpy-base/mop_model numpy-combined CF CTA 85 CTF 85
```

## Results and reruns

| File or directory | Meaning |
| --- | --- |
| `bin/<output-name>/dar_model/` | Dynamic architecture model (full and MOP-only runs). |
| `bin/<output-name>/sar_model/` | Static architecture model (full and MOP-only runs). |
| `bin/<output-name>/mop_model/` | Merged input model (full and MOP-only runs). |
| `bin/<output-name>/mab_model/` | Abstracted model (full and abstraction-only runs). |
| `bin/<output-name>/mvis_combined/mab_model-component.dot` | MVIS component dependency graph. |
| `bin/<output-name>/mvis_combined/output.svg` | Final visualization. |

The full and MOP-only modes **clear `bin/<output-name>/` before starting**. Use a new output name if you need to keep existing results. Abstraction-only mode clears only `mab_model/` and `mvis_combined/` for its chosen output name; its input model directory is not deleted.

In abstraction-only mode, if Tulip edge bundling fails, the script retries the visualization without bundling. The full pipeline exits on a Tulip visualization failure. The MOP command may return a nonzero status even when it produces an output model; check that `mop_model/` contains the expected XMI files before reusing it.

The graph shown by MVIS is a **component view**. Multiple operation-level relations may map to one visible component edge. Use the number of edges for graph-size comparisons; do not interpret a numeric DOT edge label as the total number of calls between its two components.
